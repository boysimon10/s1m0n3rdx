## Why Go for CLI tools?

Go compiles to a single static binary. No runtime, no dependencies, no version mismatch. You `go build`, you get an executable that runs anywhere. For a CLI tool that's about as good as it gets.

I've been writing Go for backend services but building a CLI felt different - the constraints push you toward thinking about UX in a way HTTP APIs don't.

## Project structure

```
├── cmd/
│   ├── root.go
│   └── deploy.go
├── internal/
│   ├── config/
│   └── runner/
└── main.go
```

The `cmd/` folder maps directly to subcommands. cobra makes this clean - each file is one command.

## The cobra setup

```go
var rootCmd = &cobra.Command{
  Use:   "mytool",
  Short: "A tool that does useful things",
}

func Execute() {
  if err := rootCmd.Execute(); err != nil {
    os.Exit(1)
  }
}
```

One thing I got wrong early: trying to do too much in `main.go`. Keep it thin - just call `Execute()`.

## Error handling

CLIs have a different contract with the user than an HTTP server. A 500 is invisible. A bad error message is the whole experience.

```go
if err != nil {
  fmt.Fprintf(os.Stderr, "error: %v\n", err)
  os.Exit(1)
}
```

## Distribution

`goreleaser` handles cross-compilation and GitHub releases in one config file. Worth setting up from the start - shipping a new version becomes a single tag push.
