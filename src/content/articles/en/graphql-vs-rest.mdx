## The wrong question

"Should I use GraphQL or REST?" is the wrong question. The right question is: who's consuming this API and what do they need?

## When REST is obviously correct

- Public API with unknown consumers
- Simple CRUD with predictable shapes
- You want HTTP caching to work naturally
- Your team knows REST and GraphQL is new overhead

REST's constraint model (resources, verbs, status codes) is a shared language. Everyone knows what a `GET /users/:id` returning a 404 means.

## When GraphQL earns its complexity

- Mobile clients on flaky connections that can't afford over-fetching
- Multiple frontends needing different data shapes from the same service
- Rapid product iteration where the schema needs to evolve without versioning

The killer feature isn't the query language. It's schema introspection - clients can discover what's available without reading docs.

## The real cost of GraphQL

N+1 queries. Every junior engineer hits this. You return a list of posts and each post resolver independently queries the author - 100 posts is 101 queries.

Dataloaders solve this but add cognitive overhead. You have to think about batching from day one.

```ts
const authorLoader = new DataLoader(async (ids) => {
  const authors = await db.users.findMany({ where: { id: { in: ids } } });
  return ids.map(id => authors.find(a => a.id === id));
});
```

## My current take

REST for anything external or team-facing. GraphQL for internal BFF layers where you control both sides and iteration speed matters.

Don't mix them at the same layer - you end up with the complexity of both.
